# Group Worker

سرویس مستقل پردازش بازی‌های گروهی؛ هم‌ساختار با `private-worker` و با Redis و MongoDB مشترک پروژه.

## ساختار کد

```text
src/
├── main.ts                    # نقطهٔ ورود
├── worker.ts                  # چرخهٔ عمر و مصرف Redis Streams
├── telemetry.ts               # سلامت و مانیتورینگ سرویس
└── core/
    ├── config.ts              # تنظیمات محیطی و تنظیمات لاگ
    ├── logger.ts              # لاگ ساختاریافتهٔ Pino و چرخش فایل‌ها
    ├── redis.ts               # اتصالات Redis مستقل
    ├── bot/ephemeral.ts      # پیام اختصاصی داخل گروه و ویرایش آن
    ├── services/timing.ts    # ثبت درخواست زمان‌بندی در Redis Stream
    ├── runtime.ts             # صادرات مشترک برای سازگاری بین ماژول‌ها
    ├── util.ts                # تشخیص فرمان کامل، قالب‌بندی و منشن
    ├── models/index.ts        # مدل‌های مشترک User/GroupConfig/GroupDuel/Ledger/House
    ├── contracts/group.ts     # نوع‌های جریان گروه و بازی
    ├── bot/
    │   ├── instance.ts        # نمونهٔ Bot API
    │   ├── updates.ts         # مسیریابی و پردازش آپدیت‌ها
    │   └── callbacks.ts       # دکمه‌ها، پنل و انتخاب حرکت
    └── services/
        ├── group.ts           # فعال‌سازی گروه، زبان، راهنما و آمار پنل
        ├── wallet.ts          # رزرو/آزادسازی اتمیک و state جریان دعوت
        ├── duel-flow.ts       # انتخاب حالت/ارز/مبلغ و ایجاد دعوت
        ├── game-message.ts   # متن بازی، پیشرفت انتخاب و پاسخ نتیجه
        └── settlement.ts     # تسویه بازی‌هایی که هر دو بازیکن انتخاب کرده‌اند
```

## اجرا

1. `.env.example` را به `.env` کپی کن و `BOT_TOKEN`، `BOT_USERNAME`، `REDIS_URL` و `MONGO_URI` را با سایر سرویس‌ها یکسان تنظیم کن.
2. MongoDB باید replica set فعال داشته باشد؛ رزرو و تسویه کیف پول در تراکنش انجام می‌شود.
3. `npm install`
4. `npm run typecheck`
5. `npm run start`
6. پس از بالا آمدن worker، `ENABLE_GROUP_UPDATES=1` را در `gateway/.env` فعال کن.
7. لاگ‌ها به‌صورت پیش‌فرض در `./logs/group-worker` ذخیره می‌شوند؛ برای لاگ‌های اطلاعاتی `LOG_LEVEL=info` تنظیم کن.

## مرز مسئولیت‌ها

- Gateway فقط فرمان‌های دقیق، callbackهای `gw:` و رویداد عضویت ربات را به `updates:groups` می‌فرستد؛ متن عادی گروه وارد صف نمی‌شود.
- Group Worker مالک جریان دعوت، پنل، تنظیمات گروه، رزرو موجودی و ثبت انتخاب‌هاست.
- Group Worker به BullMQ وابستگی ندارد: درخواست‌های timeout را روی Redis Stream مشترک `rps:timing:commands` می‌گذارد؛ BullMQ Worker تنها سرویس تولید jobهای BullMQ و اجرای timeoutهاست. همان قرارداد Stream برای private-worker نیز استفاده می‌شود.
- کارمزدهای شرطی از `Settings.main.fees` و سهم فعال‌کننده از `Settings.main.groupRewardPercent` خوانده می‌شوند؛ درصد سهم از پنل مالک ربات قابل تنظیم است.
- فرم انتخاب و پنل مدیریت به‌صورت پیام ephemeral داخل گروه برای همان کاربر نمایش داده می‌شوند؛ زبان تمام مرحله‌های فرم (حالت، ارز و مبلغ) از زبان انتخاب‌شدهٔ همان گروه پیروی می‌کند. برای شروع فرم‌ها از فرمان عادی گروه، ربات باید ادمین گروه باشد. اعلان پاداش مالی فقط به پیوی فعال‌کننده فرستاده می‌شود.
- در ۸۵٪ مهلت انتخاب، یک هشدار در گروه ارسال می‌شود و فقط بازیکنانی که هنوز سنگ/کاغذ/قیچی را انتخاب نکرده‌اند منشن می‌شوند. زمان هشدار به‌صورت durable از Redis Stream مشترک به BullMQ سپرده می‌شود و در reconciliation قابل بازیابی است.
- پایان بازی دکمه‌های انتخاب را حذف می‌کند اما متن پیام بازی را تغییر نمی‌دهد؛ نتیجه به‌صورت reply جداگانه فرستاده می‌شود و پیام «This duel has ended…» نمایش داده نمی‌شود.
- فراخوانی‌های Bot API جدید از مسیر رسمی `bot.api.raw.<method>(payload)` انجام می‌شوند؛ از `bot.api.callApi` استفاده نشده است. پیش از اولین محتوای خصوصی در هر گروه، worker قابلیت ephemeral را با یک پیام نامرئی آزمایش می‌کند و اگر پاسخ، `ephemeral_message_id` نداشته باشد، محتوای پنل را ارسال نمی‌کند.

## لاگ‌گیری و عیب‌یابی

- لاگ‌ها با Pino به‌صورت JSON ساختاریافته نوشته می‌شوند و شامل نام سرویس، PID، زمان ISO، کلید خطا و context مرتبط هستند.
- `pino-roll` چرخش روزانه و محدودیت اندازهٔ فایل را مدیریت می‌کند؛ فایل‌های قدیمی‌تر از `LOG_RETENTION_DAYS` پاک می‌شوند.
- خطاهای پرتکرار بر اساس کلید ثابت throttle می‌شوند تا لاگ پر نشود؛ تعداد رخدادهای سرکوب‌شده هنگام ثبت بعدی درج می‌شود.
- خطاهای Redis، پردازش Redis Stream، پیام ephemeral، ارسال پنل و اعلان پاداش با context قابل‌ردیابی ثبت می‌شوند. هیچ fallback نباید خطای اصلی ارسال پیام اختصاصی را بی‌صدا حذف کند.
- تنظیمات مهم: `LOG_DIR`، `LOG_LEVEL`، `LOG_MAX_SIZE`، `LOG_RETENTION_DAYS` و `LOG_THROTTLE_MS`.
- worker هنگام راه‌اندازی `getMe` را اجرا می‌کند؛ اگر `BOT_TOKEN` یا مسیر Bot API اشتباه باشد (معمولاً خطای `404 Not Found`)، قبل از مصرف پیام‌های Stream متوقف می‌شود. مقدار `BOT_TOKEN` داخل `.env` مربوط به `group-worker` را بررسی کن و آن را در لاگ یا چت منتشر نکن.

## تنظیم آسان زمان و هشدار مهلت انتخاب

در پنل مدیریت، هر چهار تنظیم زمان اکنون به یک صفحهٔ مستقل می‌روند. گزینه‌های آماده شامل ۳۰، ۳۲، ۴۵، ۶۰، ۹۰، ۱۲۰، ۱۸۰ و ۳۰۰ ثانیه هستند (گزینه‌های بیش از سقف همان نوع زمان نمایش داده نمی‌شوند) و کنترل‌های −۱/+۱، −۵/+۵ و −۱۰/+۱۰ نیز مقدار دقیق را تنظیم می‌کنند. کمینه ۳۰ ثانیه است.

وقتی دعوت پذیرفته شود، `deadline` و `reminderAt` ثبت می‌شوند؛ `reminderAt` روی ۸۵٪ مدت انتخاب قرار دارد. BullMQ Worker در آن زمان وضعیت هر دو انتخاب را دوباره می‌خواند و فقط بازیکن یا بازیکنان بدون انتخاب را در گروه منشن می‌کند.
