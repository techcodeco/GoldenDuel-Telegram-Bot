# 🎮 RPS Worker

**سامانهٔ ربات تلگرام سنگ، کاغذ، قیچی با معماری چندسرویسی**

RPS Worker یک پروژهٔ ماژولار برای مدیریت دوئل‌های دوستانه و شرطی در تلگرام است. بخش‌های پروژه در یک مخزن Git نگهداری می‌شوند، اما هر سرویس ساختار، وابستگی‌ها، تنظیمات محیطی و فرایند اجرای مستقل خود را دارد.

</div>

---

## ✨ امکانات اصلی

- دوئل دوستانه و دوئل شرطی
- مدیریت بازی، انتخاب سنگ/کاغذ/قیچی و زمان‌پایان‌ها
- مدیریت موجودی، شارژ و برداشت طبق تنظیمات پروژه
- پشتیبانی از بازی و تنظیمات گروه‌های تلگرامی
- اجرای پیام‌های انبوه از طریق سرویس جداگانه
- اجرای کارهای زمان‌بندی‌شده و یادآوری‌ها با صف
- تهیهٔ بکاپ از MongoDB و ارسال فایل بکاپ برای مالک ربات
- ثبت لاگ و گزارش اطلاعات پایهٔ سرویس‌ها
- جداسازی سرویس‌ها برای استقرار، مقیاس‌دهی و عیب‌یابی مستقل

## 🧩 ساختار مخزن

```text
project/
├── gateway/           # دریافت و مسیریابی آپدیت‌های تلگرام
├── private-worker/    # منطق ربات در گفت‌وگوی خصوصی و پنل مالک
├── group-worker/      # بازی‌ها و تنظیمات گروه‌ها
├── bullMQ-worker/     # صف‌ها، زمان‌بندی و timeoutها
├── broadcast-worker/  # اجرای پیام‌های انبوه
└── backup-worker/     # بکاپ دیتابیس و گزارش وضعیت سرویس
```

هر پوشه فایل `package.json` و تنظیمات محیطی مختص خود را دارد. وابستگی‌ها را جداگانه در همان پوشه نصب کنید؛ در ریشهٔ مخزن، وابستگی مشترک برای همهٔ سرویس‌ها در نظر گرفته نشده است.

## 🛠️ فناوری‌ها

- **TypeScript و JavaScript** برای منطق سرویس‌ها
- **Node.js** برای Workerها و **Bun** برای Gateway
- **grammY** برای ارتباط با Telegram Bot API
- **Elysia** برای لایهٔ Gateway
- **Redis و ioredis** برای ارتباط و هماهنگی بین سرویس‌ها
- **MongoDB و Mongoose** برای داده‌های برنامه
- **BullMQ** برای اجرای jobها و زمان‌بندی‌های پایدار
- **Pino** برای ثبت لاگ
- **MongoDB Database Tools (`mongodump`)** برای تهیهٔ بکاپ

## ⚙️ پیش‌نیازها

- Node.js سازگار با وابستگی‌های پروژه
- Bun برای اجرای `gateway`
- دسترسی به Redis و MongoDB
- توکن ربات تلگرام
- نصب MongoDB Database Tools روی محیطی که `backup-worker` در آن اجرا می‌شود

> قابلیت‌های تراکنشی برنامه به پیکربندی صحیح MongoDB Replica Set نیاز دارند. آدرس معرفی‌شده در تنظیمات Replica Set باید از محیط Workerها قابل‌دسترسی باشد؛ آدرس موقت IP کانتینر ممکن است پس از راه‌اندازی مجدد تغییر کند.

## 🚀 راه‌اندازی

### ۱. دریافت مخزن

```bash
git clone <REPOSITORY_URL>
cd <PROJECT_DIRECTORY>
```

### ۲. تنظیم محیط هر سرویس

برای هر سرویس، فایل نمونهٔ تنظیمات همان پوشه را کپی کنید و مقادیر واقعی را وارد کنید:

```bash
cd private-worker
cp .env.example .env
```

مقادیر توکن، آدرس Redis، اتصال MongoDB و شناسه‌های مالک را بر اساس فایل `.env.example` همان سرویس تنظیم کنید. برای هر سرویس دیگری نیز همین کار را جداگانه انجام دهید. نام متغیرها ممکن است بین سرویس‌ها متفاوت باشد؛ فایل نمونهٔ همان سرویس مرجع است.

### ۳. نصب و اجرا

**Gateway** (با Bun):

```bash
cd gateway
bun install
bun run start
```

**Workerهای Node.js** (هرکدام در پوشهٔ خودش):

```bash
cd private-worker
npm install
npm run start
```

نام پوشه را به `group-worker`، `bullMQ-worker`، `broadcast-worker` یا `backup-worker` تغییر دهید تا سرویس مربوطه را نصب و اجرا کنید. برای کامندهای دقیق ساخت، بررسی TypeScript و اجرای production به `scripts` موجود در `package.json` همان سرویس مراجعه کنید.

## 🔗 ارتباط سرویس‌ها

- سرویس‌ها می‌توانند از Redis و MongoDB مشترک استفاده کنند، ولی فرایند اجرا و وابستگی‌های آن‌ها مستقل است.
- Gateway آپدیت‌ها را دریافت و بر اساس قراردادهای پروژه به مسیرهای مربوط هدایت می‌کند.
- `private-worker` و `group-worker` منطق پیام خصوصی و گروه را از هم جدا نگه می‌دارند.
- `bullMQ-worker` کارهای صف و زمان‌بندی را اجرا می‌کند.
- `broadcast-worker` مسئول اجرای کمپین‌های پیام انبوه است.
- `backup-worker` فرایند بکاپ و امکانات مرتبط با آن را مدیریت می‌کند.

## 🔐 نکات امنیتی و استقرار

- فایل‌های `.env` واقعی را در Git ثبت نکنید.
- توکن تلگرام، رمز دیتابیس، کلید Replica Set و اطلاعات اتصال را در مخزن عمومی یا لاگ‌ها قرار ندهید.
- برای هر سرویس فقط متغیرهای موردنیاز خودش را تنظیم کنید.
- در محیط عملیاتی، دسترسی شبکه به Redis و MongoDB را محدود کنید و بکاپ‌ها را به‌طور دوره‌ای آزمایش بازیابی کنید.
- پیش از انتشار نسخهٔ جدید، سرویس‌ها را در محیط آزمایشی اجرا و لاگ‌های شروع به کار را بررسی کنید.
