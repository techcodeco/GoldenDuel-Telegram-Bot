# RPS Worker — separated services

این پوشه دیگر یک برنامهٔ یکپارچه نیست. هر سرویس پروژهٔ مستقل خودش را دارد: فایل‌های سورس، `package.json`، تنظیمات TypeScript و `.env` مخصوص همان سرویس.

## ساختار

```text
project/
├── gateway/          # Gateway اصلی ارسالی شما؛ Bun + Elysia
├── private-worker/   # منطق ربات و پیام‌های خصوصی
├── bullMQ-worker/    # اجرای jobهای زمان‌بندی و timeoutهای دوئل
├── broadcast-worker/ # اجرای کمپین‌های پیام انبوه
├── group-worker/     # مصرف‌کننده آپدیت‌های گروه، تنظیمات، دوئل و پنل گروه
└── backup-worker/    # بکاپ مستقل MongoDB به ZIP در تلگرام
```

هیچ `src/` یا `package.json` مشترکی در ریشه وجود ندارد. برای هر سرویس جداگانه dependency نصب می‌شود. `private-worker/package.json` عمداً وابستگی `bullmq` ندارد: این سرویس درخواست‌های زمان‌بندی را در Redis Stream می‌نویسد و فقط `bullMQ-worker` آن‌ها را به صف BullMQ تبدیل می‌کند. به همین ترتیب، private-worker درخواست کمپین پیام انبوه را در Redis Stream ثبت می‌کند و فقط `broadcast-worker` آن را وارد صف BullMQ می‌کند.

## مسئولیت سرویس‌ها

- **gateway**: همان کد Gateway موجود در فایل ZIP ارسالی شما بر پایهٔ Bun و Elysia حفظ شده است؛ منطق route/filter، پردازش webhook، streamها و تنظیماتش بازنویسی نشده‌اند. فقط گزارش‌دهی مانیتورینگ سرور به آن اضافه شده است.
- **private-worker**: پردازش پیام‌های خصوصی، منوها، پنل مالک، پرداخت‌ها، کیف پول، تنظیمات، matchmaking و منطق بازی.
- **bullMQ-worker**: زمان‌بندی timeout/reminder، بازیابی jobها و مصرف درخواست‌های زمان‌بندی از `rps:timing:commands`.
- **broadcast-worker**: اجرای کمپین‌ها، rate limit ارسال، نگهداری heartbeat و مصرف فرمان‌های صف از `rps:broadcast:commands`.
- **group-worker**: فقط کلمات کلیدی دقیق، دکمه‌های `gw:` و رویداد اضافه/حذف ربات را از Stream گروه مصرف می‌کند؛ پیام‌های عادی گروه در Gateway حذف می‌شوند. این worker تنظیمات و آمار گروه، دعوت، رزرو موجودی، انتخاب سنگ‌کاغذ‌قیچی و تسویه بازی گروهی را مدیریت می‌کند. timeoutهای دعوت و بازی را به Redis Stream مشترک `rps:timing:commands` می‌فرستد؛ تنها `bullMQ-worker` این فرمان‌ها را به jobهای BullMQ تبدیل و اجرا می‌کند.
- **backup-worker**: به کمک `mongodump` یک dump معمولی BSON برای کالکشن‌ها می‌سازد، پوشهٔ dump و `manifest.json` را داخل ZIP قرار می‌دهد و مستقیماً در تلگرام برای مالک می‌فرستد. ZIPهای بزرگ‌تر از سقف فایل تلگرام به بخش‌های شماره‌دار تقسیم می‌شوند. فقط نمایهٔ بکاپ و `file_id`ها در Redis نگهداری می‌شوند؛ دیتابیس دوم یا Cloud storage لازم نیست. پنل مالک تاریخچهٔ صفحه‌بندی‌شده، دانلود دوباره، تنظیم فاصله و اجرای دستی دارد؛ watchdog آفلاین‌شدن Worker را هشدار می‌دهد.

## مانیتورینگ سرورها

سرویس‌های قابل اجرا هر ۵ ثانیه اطلاعات CPU، RAM، دیسک فایل‌سیستم، نام سرور، نام instance، نوع سرویس، PID و زمان نمونه‌گیری را در Redis ثبت می‌کنند. پنل مالک در ربات این اطلاعات را از Redis می‌خواند و instanceها را بر اساس `SERVER_NAME` گروه‌بندی می‌کند؛ بنابراین ممکن است روی ۱۰ سرور ۲۰ یا تعداد بیشتری worker instance داشته باشید و آن‌ها به شکل ۱۰ سرور نمایش داده شوند.

- تمام سرویس‌هایی که روی **یک ماشین فیزیکی** اجرا می‌شوند باید `SERVER_NAME` یکسان داشته باشند؛ روی ماشین‌های متفاوت، این مقدار را متفاوت قرار دهید.
- `INSTANCE_NAME` اختیاری است؛ در صورت خالی بودن نام یکتایی بر اساس سرویس، hostname و PID ساخته می‌شود. پنل مالک، namespace، hostname، نام instanceها، PID و نام سرویس هر instance را نیز نشان می‌دهد. اگر `backup-worker` فعال باشد، زمان آخرین بکاپ موفق، اندازه و مسیر فایل نیز در همان پنل دیده می‌شود.
- `MONITORING_NAMESPACE` در فایل‌های این بسته به‌صورت یکسان روی `rps-worker-main` تنظیم شده است. برای هر بات مستقل که Redis مشترک دارد، یک مقدار یکتای متفاوت انتخاب و در تمام سرویس‌های همان بات یکسان قرار دهید. متغیرهای `BOT_TOKEN` برای عملکرد خود ربات نیز باید با توکن درست همان بات پر شوند.
- با خاموش شدن یا از دسترس خارج شدن یک instance، رکورد آن پس از انقضای TTL از داشبورد حذف می‌شود. اندازهٔ دیسک مربوط به فایل‌سیستمی است که مسیر اجرای سرویس روی آن قرار دارد؛ در کانتینرها ممکن است منابع گزارش‌شده منابع قابل‌مشاهده از کانتینر باشند نه کل میزبان.
- مانیتورینگ `group-worker` باید پس از تنظیم متغیرهای محیطی و اجرای سرویس بررسی شود؛ worker از Redis و MongoDB مشترک استفاده می‌کند.

## راه‌اندازی مستقل

برای هر پوشه، فایل `.env.example` همان پوشه را به `.env` کپی کنید و تنظیمات آن سرویس را پر کنید. فایل‌های `.env` عملیاتی عمداً داخل بستهٔ قابل‌اشتراک قرار نگرفته‌اند؛ توکن‌ها و رمزهای واقعی را فقط روی سرور مقصد وارد کنید. Redis، MongoDB و `BOT_TOKEN` باید مطابق محیط شما تنظیم شوند. نام Streamها هم باید بین producer و consumer مربوطه یکسان باشد.

### Gateway (Bun)

```bash
cd gateway
bun install
bun run start
```

### private-worker

```bash
cd private-worker
npm install
npm run start
```

### bullMQ-worker

```bash
cd bullMQ-worker
npm install
npm run start
```

### broadcast-worker

```bash
cd broadcast-worker
npm install
npm run start
```

جزئیات رفتار و آزمون‌های انجام‌شده در `GROUP_WORKER_IMPLEMENTATION_FA.md` آمده است. فرم انتخاب حالت/ارز/مبلغ و پنل مدیریت با قابلیت جدید Telegram Ephemeral Messages در همان گروه و فقط برای فرد مربوطه نمایش داده می‌شوند. برای این قابلیت، Bot API و کلاینت تلگرام باید پشتیبانی کنند و ربات در گروه باید administrator باشد؛ پیام‌های دعوت و بازی برای همهٔ اعضا عمومی هستند.

### backup-worker (MongoDB → BSON directory → ZIP → Telegram)

```bash
cd backup-worker
cp .env.example .env
# MONGO_URI, BOT_TOKEN, OWNER_IDS و Redis/namespace مشترک را تنظیم کن
npm install
npm run typecheck
npm test
npm run build
npm start
```

پیش‌نیاز: MongoDB Database Tools و فرمان `mongodump` روی سرور نصب باشد. مالک باید ابتدا در پیوی ربات `/start` بزند تا بتواند فایل دریافت کند. فاصلهٔ آغازین بکاپ با `BACKUP_INTERVAL_MINUTES` (پیش‌فرض ۱۵ دقیقه، بازهٔ ۱ تا ۱۴۴۰) تعیین می‌شود؛ پس از اجرا می‌توان از پنل مالک → «مدیریت بکاپ‌ها» آن را در دقیقه تغییر داد، بکاپ دستی گرفت، وضعیت آنلاین/آفلاین را دید و تاریخچه را صفحه‌بندی/دانلود کرد. ZIP حاوی `manifest.json` و `dump/<database>/<collection>.bson.gz` است و با `mongorestore --uri="$RESTORE_MONGO_URI" --gzip --drop restore-point/dump` بازیابی می‌شود. فایل‌هایی که از سقف ۴۹ MiB بیشتر هستند به چند بخش ارسال می‌شوند؛ قبل از unzip باید بخش‌ها به یک فایل ZIP متصل شوند. جزئیات در `backup-worker/README.md` و `INTEGRATED_BACKUP_AND_UI_GUIDE_FA.md` آمده است.
### group-worker

```bash
cd group-worker
cp .env.example .env
npm install
npm run typecheck
npm test
npm run build
npm run start
```

برای فعال‌سازی دریافت رویدادهای گروهی، پس از اطمینان از اجرای group-worker مقدار `ENABLE_GROUP_UPDATES=1` را در `gateway/.env` قرار بده. `BOT_TOKEN`، `REDIS_URL` و `MONGO_URI` باید با سرویس‌های دیگر یکسان باشند. `TIMING_COMMAND_STREAM` در group-worker و bullMQ-worker باید یکسان باشد (پیش‌فرض `rps:timing:commands`). group-worker به BullMQ وابسته نیست؛ فقط bullMQ-worker باید روشن باشد تا timeoutها را اجرا کند. هر دو worker گروه و BullMQ به MongoDB replica set نیاز دارند تا عملیات رزرو و تسویه تراکنشی باشد. برای فرم‌ها و داشبورد اختصاصی داخل گروه، به ربات دسترسی administrator بده.

## پیش‌نیازهای انتشار

1. ابتدا Redis و MongoDB را آماده کنید.
2. مقدار `BOT_TOKEN` را در تمام سرویس‌هایی که متعلق به همین بات هستند با توکن واقعی همان بات پر کنید. مقدار `MONITORING_NAMESPACE` نیز باید در همهٔ سرویس‌های این بات یکسان باشد؛ در این بسته مقدار پیش‌فرض `rps-worker-main` است.
3. `SERVER_NAME` را بر اساس ماشین مقصد تنظیم کنید.
4. `gateway/.env` را با مقادیر واقعی webhook/Redis خود بررسی کنید. کد Gateway ارسالی شما حفظ شده است؛ حالت اجرا و تنظیمات webhook طبق فایل خودش هستند.
5. برای فعال شدن کمپین پیام انبوه، دست‌کم یک instance از `broadcast-worker` باید روشن بماند. پنل مالک این شرط را از heartbeat زنده بررسی می‌کند و در نبود worker اجازهٔ آغاز کمپین نمی‌دهد.
6. برای بکاپ، `backup-worker/.env` را کامل کنید، ابزار `mongodump` را نصب کنید، مالک در پیوی ربات `/start` بزند و `backup-worker` را روشن نگه دارید. پس از دیدن ZIP در تلگرام، حتماً فرآیند restore را در محیط staging تمرین کنید.

این بسته ساختار سرویس‌ها را تفکیک می‌کند؛ قبل از انتشار نهایی، `npm install`، `npm run typecheck` و اجرای آزمایشی را روی محیط مقصد انجام دهید.

## تغییرات پنل و تجربهٔ کاربری گروه/پیوی

- در پنل مدیریت گروه، برای هر یک از چهار مهلت (دعوت شرطی، دعوت دوستانه، انتخاب شرطی و انتخاب دوستانه) دکمهٔ ورود زمان دلخواه و دکمه‌های افزایش/کاهش ۱۰ ثانیه‌ای وجود دارد. با ارسال عدد صحیح در گروه می‌توان دقیقاً ۳۱، ۳۲، ۳۳ ثانیه و ... را تنظیم کرد؛ پیام عددی پس از دریافت حذف می‌شود. محدودهٔ مهلت دعوت ۳۰ تا ۳۰۰ ثانیه و مهلت انتخاب ۳۰ تا ۶۰۰ ثانیه است.
- هشدار انتخاب سنگ/کاغذ/قیچی در ۸۵٪ زمان کل ایجاد می‌شود؛ فقط بازیکنانی که هنوز انتخاب نکرده‌اند منشن می‌شوند و اگر هر دو انتخاب نکرده باشند، هر دو منشن خواهند شد. زمان‌بندی از Redis Stream مشترک عبور می‌کند و در `bullMQ-worker` اجرا/بازیابی می‌شود.
- اعلان پاداش گروه فارسی و انگلیسی توضیح می‌دهد که پاداش بابت تکمیل یک دوئل در گروه است؛ عبارت مبهم «پاداش فعالسازی گروه به کیف پول واریز شد» استفاده نمی‌شود.
- دستور `/start` در پیوی، در صورت پشتیبانی Telegram Bot API/کلاینت، واکنش ⚡ می‌گیرد. دکمهٔ دوئل آبی (`primary`)، واریز سبز (`success`) و برداشت قرمز (`danger`) است؛ رنگ‌ها با سبک بومی دکمه‌های تلگرام اعمال می‌شوند و به پشتیبانی کلاینت وابسته‌اند.

## ارزهای فعال و نمایش صف شرط
- ارزهای فعال ربات فقط `IRT` (تومان) و `TON` (تون/گرام) هستند.
- در انتخاب مبلغ شرط، کنار مبلغی که برای همان ارز در صف انتظار حریف دارد، نشانگر `(⌛)` نمایش داده می‌شود. کلیک روی همان مبلغ همچنان از مسیر اتمیک matchmaking عبور می‌کند و در صورت وجود حریف منتظر، اتصال مستقیم انجام می‌شود.

## کارمزد ثابت برداشت
- در پنل مدیریت ربات، دو تنظیم جدید برای «کارمزد برداشت تومان (بین‌بانکی)» و «کارمزد شبکه TON» وجود دارد. این مبالغ ثابت هستند، درصدی نیستند و به‌ترتیب با واحد تومان و TON وارد می‌شوند؛ برای TON مقدار `0.01` یعنی `0.01 TON` (با ذخیره‌سازی داخلی نانو‌تون).
- مقدار پیش‌فرض هر دو کارمزد صفر است؛ مالک/مدیر می‌تواند از پنل آن‌ها را تغییر دهد و با واردکردن `0` غیرفعال کند.
- کاربر قبل از ثبت نهایی، مبلغ کسرشده، کارمزد و مبلغ خالص دریافتی را تأیید می‌کند. فاکتور مالک نیز مبلغ خالص قابل‌پرداخت و کارمزد را جداگانه نمایش می‌دهد. کارمزد فاکتور در زمان ساخت درخواست ذخیره می‌شود تا تغییر بعدی تنظیمات روی درخواست‌های قبلی اثر نگذارد.
- درخواست ردشده کل مبلغ ناخالص را به موجودی کاربر برمی‌گرداند و کارمزد دریافت نمی‌شود؛ در درخواست پرداخت‌شده، کارمزد در حساب کارمزد سیستم ثبت می‌شود.


## فیلتر کلمات و جریمهٔ ثابت در چت دوئل
- فهرست کلمات فیلترشده را با دستورهای `/words add کلمه`، `/words del کلمه` و `/words list` مدیریت کنید.
- تشخیص کلمه پس از یکسان‌سازی حروف فارسی/عربی، حذف اعراب و نشانه‌های نگارشی انجام می‌شود؛ بنابراین قراردادن علامت‌هایی مانند `.!#-*$™` میان حروف، فیلتر را دور نمی‌زند. برای واژه‌های کوتاه، نشانه‌ها حذف می‌شوند اما مرز فاصلهٔ بین واژه‌های مستقل حفظ می‌شود تا خطای مثبت بی‌دلیل کمتر شود.
- در پنل مدیریت → تنظیمات، دو مبلغ ثابت وجود دارد: «جریمه کلمات ممنوع تومان» و «جریمه کلمات ممنوع TON». برای TON مقدار با واحد TON وارد می‌شود (مثلاً `0.01`). مقدار پیش‌فرض هر دو صفر است؛ صفر یعنی فقط پیام هشدار داده می‌شود و جریمه مالی اعمال نمی‌شود.
- جریمهٔ مالی فقط در دوئل شرطی فعال است؛ در دوئل دوستانه که شرط مالی ندارد، پیام فیلترشده فقط هشدار می‌گیرد. جریمه از موجودی **قابل‌استفاده** کاربر و به ارز همان دوئل کسر می‌شود و به حساب درآمد سیستم منتقل می‌شود؛ موجودی رزروشدهٔ شرط دست‌کاری نمی‌شود.
- اگر موجودی قابل‌استفاده برای پرداخت تمام جریمه کافی نباشد، پیام همچنان ارسال نمی‌شود، اما مبلغی کسر نمی‌شود و کاربر علت را می‌بیند. هر پیام تلگرامی حداکثر یک بار جریمه می‌شود، حتی اگر همان آپدیت دوباره پردازش شود.
